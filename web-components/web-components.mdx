# Web Components

These stories demonstrate consuming YaleSites components **outside Drupal** as framework-neutral
[custom elements](https://developer.mozilla.org/en-US/docs/Web/API/Web_components) (part of epic
[#1351](https://github.com/yalesites-org/YaleSites-Internal/issues/1351)). Two components are shown —
a static one (**Divider**) and an interactive one with JavaScript behavior (**Accordion**) — each
implemented **two ways** so you can compare:

<ul>
  <li><strong>Lit</strong> — built with the <a href="https://lit.dev">Lit</a> library (source in <code>web-components/src/</code>).</li>
  <li><strong>Vanilla</strong> — the same components hand-written with only the native Custom Elements + Shadow DOM APIs, no framework (source in <code>web-components/vanilla/</code>).</li>
</ul>

Both render **identical output** (same markup, same styles, same behavior) — the difference is the
code that produces it. Open <strong>Lit → Accordion</strong> and <strong>Vanilla → Accordion</strong>
side by side, then read the two source files to see what Lit does for you.

These are demonstration/comparison artifacts, not a maintained second distribution. The Drupal site
and Storybook's Twig components are unchanged — this is purely additive.

## Lit vs. vanilla: what Lit buys you

<table>
  <thead>
    <tr><th>Concern</th><th>Lit (<code>src/</code>)</th><th>Vanilla (<code>vanilla/</code>)</th></tr>
  </thead>
  <tbody>
    <tr>
      <td>Templating</td>
      <td>Declarative <code>html`…`</code> with a diffing renderer</td>
      <td>Hand-built <code>innerHTML</code> strings; manual escaping of interpolated text</td>
    </tr>
    <tr>
      <td>Reactivity</td>
      <td>Reactive properties/attributes re-render automatically</td>
      <td>Manual <code>observedAttributes</code> + <code>attributeChangedCallback</code> and an <code>items</code> setter that re-renders by hand</td>
    </tr>
    <tr>
      <td>Pre-upgrade props</td>
      <td>Recovered automatically (a property set before the element is defined still applies)</td>
      <td>Must call <code>_upgradeProperty()</code> in <code>connectedCallback</code>, or a property set before upgrade shadows the accessor and is silently lost</td>
    </tr>
    <tr>
      <td>Events</td>
      <td>Declarative <code>@click</code> bindings in the template</td>
      <td>Manual <code>addEventListener</code>, re-wired on each structure rebuild</td>
    </tr>
    <tr>
      <td>Efficient updates</td>
      <td>Diffing updates only what changed (focus preserved on toggle for free)</td>
      <td>We do <strong>targeted attribute updates</strong> by hand to avoid the focus loss a full re-render would cause</td>
    </tr>
    <tr>
      <td>Rich content</td>
      <td><code>unsafeHTML(content)</code></td>
      <td>Raw <code>innerHTML</code> (same trust model — sanitize untrusted HTML)</td>
    </tr>
    <tr>
      <td>Dependency</td>
      <td>~5&nbsp;KB Lit runtime</td>
      <td>None (pure platform)</td>
    </tr>
  </tbody>
</table>

The vanilla <strong>Divider</strong> is nearly as short as the Lit one (it is static). The vanilla
<strong>Accordion</strong> is noticeably more code — the manual state-to-DOM wiring, event binding,
and targeted updates are exactly the work Lit handles for you. That gap is the trade-off to weigh.

## Theming

Both implementations use Shadow DOM and theme via **CSS custom properties**, which inherit through
the shadow boundary — so the Yale design tokens (loaded globally in Storybook) reach the components,
and the toolbar <strong>Site: Global Theme</strong> control re-themes them. Each component also ships
<code>var(--token, fallback)</code> fallbacks so it renders correctly with no token stylesheet.
