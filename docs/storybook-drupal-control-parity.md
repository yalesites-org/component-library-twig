# Storybook / Drupal control parity audit

An inventory of every control the component library exposes in Storybook, and whether a
YaleSites site builder can actually produce that state in Drupal.

Produced for yalesites-org/YaleSites-Internal#1661, part of the Color Surface epic
(yalesites-org/YaleSites-Internal#1634).

## Why this exists

Storybook has drifted from what the platform ships. Controls get added to a story or a props
file during design exploration and never make it into the Drupal paragraph, block config or
SDC prop, so Storybook offers options the CMS does not. That is not just untidy: the colour
work is spending real effort fixing contrast on component states no editor can ever create.

The divider is the case that prompted the ticket. Storybook lets you set line thickness and
line colour; Drupal offers width and position and nothing else. Every contrast combination
generated by those two controls is unreachable.

This document is the full inventory so the team can decide, control by control, whether to
migrate it into Drupal, drop it from Storybook, or keep it deliberately.

## How to read the table

One row per control. Columns:

| Column | Meaning |
| --- | --- |
| **Tier** | Atom / Molecule / Organism. |
| **Component** | The Storybook title path the control appears under. |
| **Control** | The key in the component's `*-props.yml` — the arg name in Storybook. |
| **Label** | The human label Storybook shows for it. |
| **Twig prop** | The Twig variable, CSS custom property or data attribute it drives. |
| **Storybook options** | The **effective** option set. Where a `*.stories.js` overrides the props file (20 controls do — usually pulling the list from the tokens package), this is the override, not what the props file declares. |
| **Status** | See the table below. |
| **Drupal control** | Precisely where the editor-facing control lives, when there is one. |
| **Drupal options** | The option set Drupal actually offers, where the two are comparable. |
| **Recommended disposition** | A *recommendation only* — see "This does not decide anything". One of `Migrate to Drupal`, `Drop from Storybook`, `Add to Storybook`, `Keep as-is`. |
| **Ratified** | Deliberately blank. Filled in during the review. |
| **Colour surface** | `Yes` when this control varies a foreground/background colour or a theme selection **and** is unreachable or partially reachable — i.e. contrast effort spent on it is wasted. |
| **Notes** | The evidence that settles the row, with `file:line`. |
| **Source** | The props file the control is declared in. |

### Status values

| Status | Meaning |
| --- | --- |
| `Wired` | An editor-facing Drupal control exists with an equivalent option set. |
| `Partial` | It exists on both sides, but the option sets differ — in **either** direction. Both counts are given so you can see which way. |
| `Storybook-only` | No editor can produce this state. |
| `Drupal-only` | An editor control exists with no Storybook counterpart — drift the other way. |
| `Content` | Not a style or config control at all, just a content slot Drupal fills from field data (a heading, a body, an image, a URL). Listed for completeness; skip these when reviewing. |
| `Structural` | Twig-internal plumbing (a base class, an extra-classes hook, a nested render slot). Not an editor control and should not become one. |

`Content` and `Structural` exist so the review can get to the interesting rows fast. The rows
that need a decision are `Storybook-only`, `Partial` and `Drupal-only`.

### Recommended dispositions

| Disposition | Meaning |
| --- | --- |
| `Migrate to Drupal` | The capability is wanted and the only thing missing is the field or setting. |
| `Drop from Storybook` | The control implies a CMS option that does not exist and is not wanted. Its presence is misleading, and in the colour cases it is generating contrast combinations nobody can produce. |
| `Add to Storybook` | **Reverse drift.** Drupal already offers an option Storybook does not render, so the option ships to editors and is never previewed or contrast-checked. The fix is in the props file, not in Drupal. |
| `Keep as-is` | The mismatch is deliberate: the control documents a real design capability, supports a visual-regression story, or is driven by a sitewide setting or by content rather than by a per-instance choice. The reason is in the Notes column. |

`Add to Storybook` is not in the ticket's original three-way framing. It was added because a
real and slightly alarming category turned up: options an editor can pick **today** that
Storybook never shows. Those are worse than the drift the ticket set out to find — the ticket's
Storybook-only controls waste effort on states nobody can reach, whereas these are reachable
states nobody is checking.

## This does not decide anything

Every value in **Recommended disposition** is a recommendation for the review to accept,
reject or change. The ticket is explicit that dispositions are ratified with the lead
developer and design, and that the migrate/drop implementation and its follow-up tickets are
**not** part of this work. The **Ratified** column is left blank on purpose — fill it in
during the review, then raise the follow-up tickets for whatever is agreed, tagged
`color-surface-followup`.

## Method

The inventory is derived from source, not from clicking through the Storybook controls panel:

1. **Storybook side.** Every control in every `*-props.yml` under `01-atoms`, `02-molecules`
   and `03-organisms`. These files are the declared single source of truth for both the
   Storybook `argTypes` and the MDX props tables (`_storybook/component-props.js`), so they
   are the complete list — including controls the panel hides. Each `*.stories.js` was then
   read for `argTypes.<x> = {...}` overrides that change the effective option set.
2. **Drupal side.** For each control's Twig prop: the `atomic/templates/**` template that
   renders the component (the only place a Drupal value is actually passed in), the
   `field.field.block_content.*` / `field.field.paragraph.*` / `field.field.node.*` configs,
   the matching `core.entity_form_display.*` (a field can exist and still be hidden from the
   form), `ys_themes.component_overrides.yml` for the five style dials, the sitewide
   `ys_themes` settings form for site chrome, and Views Basic's exposed options.
3. A literal search for each Twig prop across those corpora produced candidates; every row
   was then confirmed by reading the templates, because a template can pass a value under a
   different local name, through an `embed ... with` alias, or from a preprocess function.

Spot-checked against the running site rather than only against exported config: the divider
case was confirmed via the live entity form display and the live
`ys_themes_allowed_values_function` output, which is what an editor actually sees.

## Headline findings

**The drift is real, it is bigger than the divider, and it runs in both directions.**

1. **Seven components paint a colour an editor cannot choose.** `Image Banner` `bgColor`,
   `Tabs` `tabsTheme`, `Profile Meta` `bgColor`, `Pull Quote` `accentTheme`, `Divider`
   `dividerColor`, `Tile Item` `iconName`, `Utility Nav` `ctaTheme` — each offers a theme or
   colour selection in Storybook that no Drupal field, dial or setting feeds. Every contrast
   combination those controls generate is unreachable, and the colour effort spent on them is
   spent on nothing. They do **not** all get the same recommendation — four are recommended for
   dropping and three for building the missing field. See the Color Surface section below.

2. **Three of those are "dead wiring", not merely missing fields — and that distinction
   changes the fix.** `block--inline-block--image-banner.html.twig:9` reads
   `content.field_style_color`, `block--inline-block--facts.html.twig:12` reads
   `content.field_style_variation`, and `block--inline-block--cta-banner.html.twig:16-17` read
   `field_button_alignment` / `field_button_style_consistency` — **none of those fields exist
   on those block types.** The Twig already expects the value, so these are the cheapest
   `Migrate to Drupal` candidates in the audit: add the field and the wiring is done. It also
   means somebody intended these and the field never landed.

3. **Reverse drift is the more dangerous half, and the ticket did not anticipate it.**
   14 controls expose **fewer** options in Storybook than Drupal actually ships. The clearest
   pattern: six components read their theme list from `Object.keys(tokens['component-themes'])`,
   which has five entries, while the matching `ys_themes` dial offers six — and component
   theme `six` has real SCSS in `link-grid`, `tile-item` and `facts-and-figures-group`. Same
   story for the section theme: `YSLayoutOptions.php:86-101` offers six section themes and
   every `*-props.yml` hardcodes five. These are editor-reachable colour pairings that are
   **never previewed and never contrast-checked** — the inverse of wasted effort, and worse,
   because the gap is invisible.

4. **Some "controls" are inert on both sides.** `component-wrapper` declares `component_width`
   while its Twig reads `component_wrapper__width`; `secondary-nav` declares `menu_theme` while
   its Twig reads `menu__theme`; `event_meta__address` is never read by the template both
   Drupal and the story actually render; `page_title__prefix` is passed by nobody. These are
   not parity problems, they are broken props that look like features.

5. **Nearly half the rows (129 of 292) are `Content` or `Structural` and need no decision.**
   Most of what Storybook exposes is a content slot Drupal fills from field data. Separating
   them out is what makes the 77 rows that *do* need a decision reviewable in one sitting.

## What this means for the Color Surface epic

**21 rows are flagged as costing the colour effort.** They are not one problem — they fall into piles that want different responses, so the counts below are grouped by what the audit recommends rather than lumped together.

### Stop chasing these — 6 (Drop from Storybook)

No editor can produce these states and the recommendation is to remove the control, so any AA failure they generate is not a real defect. This is the answer to the ticket's "call out any control currently consuming colour-surface effort" — recommend deprioritising them in the active phases, pending ratification.

- `Divider` `dividerColor` — `Storybook-only`. It recolours the rule against every section background, and none of the three values is editor-reachable, so contrast work on them is wasted.
- `Profile Meta` `bgColor` — `Storybook-only`. Sets data-component-theme on the whole profile banner (background plus heading/title/pronoun text) and five of the six themes are unreachable, so contrast work on them is wasted.
- `Pull Quote` `accentTheme` — `Storybook-only`. Drives data-component-theme (accent bar and quote-mark color against the block background) yet only theme 'one' ever renders in Drupal, so contrast checks on two/three are unreachable states.
- `Tile Item` `iconName` — `Storybook-only`. It drives an icon whose fill is a themed foreground color (--color-tile-item-content) in a variant Drupal cannot render.
- `Tile Item` `presentationStyle` — `Partial`. The icon variant paints an extra foreground glyph (fill: --color-tile-item-content, _yds-tile-item.scss:221-225) in a state no tile can reach, so its contrast checks are wasted.
- `Wrapped Callout` `themeColor` — `Partial`. The 'default' option is unreachable AND unstyled, so any contrast reading taken on it describes a surface that exists nowhere.

### Start checking these — 11 (Add to Storybook)

The opposite problem, and the one the ticket did not anticipate. Every one of these is an editor-reachable colour state that Storybook does not render, so it has never been contrast-checked at all. Missed coverage, not wasted coverage.

- `Controls` `sectionTheme` — `Partial`. Varies the section background/foreground theme; Storybook cannot render the editor-reachable 'five' section, so that combination is never contrast-checked.
- `Divider` `sectionTheme` — `Partial`. Varies the section background/foreground theme; Storybook cannot render the editor-reachable 'five' section, so that combination is never contrast-checked.
- `Forms` `sectionTheme` — `Partial`. Varies the section background/foreground theme; Storybook cannot render the editor-reachable 'five' section, so that combination is never contrast-checked.
- `Images` `sectionTheme` — `Partial`. Varies the section background/foreground theme; Storybook cannot render the editor-reachable 'five' section, so that combination is never contrast-checked.
- `Lists` `sectionTheme` — `Partial`. Varies the section background/foreground theme; Storybook cannot render the editor-reachable 'five' section, so that combination is never contrast-checked.
- `Video Background` `sectionTheme` — `Partial`. Varies the section background/foreground theme; Storybook cannot render the editor-reachable 'five' section, so that combination is never contrast-checked.
- `Callout` `backgroundColor` — `Partial`. Inverse gap - editors can pick theme six but Storybook cannot render it, so that background/foreground pairing is never contrast-checked.
- `Link grid` `themeColor` — `Partial`. Theme six is editor-selectable and has real CSS but cannot be previewed or contrast-checked in Storybook for this component.
- `Quote Callout` `accentTheme` — `Partial`. Theme 'six' is selectable in Drupal but absent from the Storybook option list, so the sixth accent/background pairing is never previewed or contrast-checked.
- `Tile Item` `themeColor` — `Partial`. Theme six is fully reachable in the CMS and styled in SCSS but is never rendered in Storybook, so its contrast pairs go unchecked.
- `Facts and Figures Group` `themeColor` — `Partial`. Inverse gap - the Drupal dial offers component theme six (which has real SCSS at _yds-facts-and-figures-group.scss:101) but the story override caps the control at five, so theme six never gets a Storybook contrast preview.

### Unreachable today, but do not delete them — 3 (Migrate to Drupal)

Also unreachable, so contrast work on them is wasted **right now** — but unlike the first pile the recommendation is to build the missing field rather than drop the control. Deprioritise the contrast work; do not treat that as agreement to remove them.

- `Image Banner` `bgColor` — `Storybook-only`. It sets data-component-theme on the whole banner (background plus the video control colours) and not one of the six values is editor-reachable, so contrast work on them is wasted.
- `Utility Nav` `ctaTheme` — `Storybook-only`. It sets data-cta-theme on the header CTA button (yds-cta.twig:27-29), and because Drupal never passes it every reachable header CTA is data-cta-theme='none' - contrast tuning of any other value is unreachable.
- `Tabs` `tabsTheme` — `Storybook-only`. A full color-theme dial that no editor can set - every Drupal tabs block renders data-component-theme=one, so contrast work on themes two-five (and six, which the SCSS styles) tests states that cannot exist.

### Deliberate — 1 (Keep as-is)

Flagged so the mismatch is visible, but the recommendation is to leave it. See the row's Notes.

- `Taxonomy Display` `componentTheme` — `Partial`. The 'default' (no-color) surface is only reachable on a block never saved through the form, so contrast pairs demoed for it are largely unproducible.

### A live bug found alongside these, not a disposition

**Five theme CSS custom properties are emitted broken on every page.** `ys_themes.module` reads `accent_color`, `action_color`, `line_color`,
`line_thickness` and `pull_quote_color` via `getSetting()`, but
`ThemeSettingsManager::THEME_SETTINGS` declares none of them. Confirmed against the running
site: the inline theme CSS contains `--color-theme-accent: var(--color-);`,
`--color-theme-action: var(--color-);`, `--color-theme-divider: var(--color-);`,
`--color-theme-pull-quote-accent: var(--color-);` and
`--thickness-theme-divider: var(--thickness-divider-);`.

This is not an audit artifact — it is a live bug, and it explains *why* divider thickness,
divider colour and the pull-quote accent are unreachable: the settings that drove them were
removed and the CSS emitter was never updated. `--color-theme-pull-quote-accent` resolving to
nothing is squarely a colour-surface concern. Recommend raising it as its own ticket rather than
holding it until ratification — it is a bug, not a disposition, so it is not waiting on
anything this review decides. Whether to restore the settings or delete the emitter is a
design call, not an inventory one.

## Related drift found on the way

Not part of the control inventory, but found while verifying it and cheaper to write down than
to rediscover:

- **The `ys_themes` module's `config/install` copy of the dials has drifted from deployed
  config.** `config/sync/ys_themes.component_overrides.yml` (byte-identical to the live active
  config) adds `button_link` entirely, redefines `content_spotlight.field_style_variation` as
  `inline`/`offset` and adds `content_spotlight.field_focus`, and adds
  `grand_hero.field_style_position: contained-narrow` and
  `grand_hero.field_style_variation: mini`. Treat `config/install` as unreliable for "what
  options exist" — this audit uses `config/sync`.
- **The divider thickness control disagrees with itself in four places.**
  `divider-props.yml` declares 8 options (`hairline,1,2,4,8,16,24,32`); the stories override
  resolves to the 7 real token keys (`0,1,2,4,6,8,hairline`); `theme-constants.js:118` carries
  a comment claiming 8 values including `16,24,32`, which do not exist in the tokens package;
  and `divider.mdx` says "Six thickness options". Worth fixing whatever the disposition.
- **The Two Column (70/30) section can never be themed or given a divider, and every other
  multi-column section can.** A colour-surface disposition rather than plain drift — whether a
  70/30 section should be themeable is a design call the review needs to make. Evidence, and
  the separate `data-component-padding` divergence it turned up, are under "Two Column (70/30)"
  in Coverage, where the disposition argument lives; they are not repeated here so there is
  only one copy of the `yalesites-project` line references to keep current.
- **An orphaned dial entry.** `ys_themes.component_overrides.yml` defines
  `quick_links.field_style_variation` (`promotional`/`subtle`), but `block_content.quick_links`
  has no such field and `block--inline-block--quick-links.html.twig:14` hardcodes
  `'promotional'`.
- **A likely embed bug.** Several ys_embed source plugins set `displayAttributes['width']` to
  the literal `'100%'` (`MicrosoftForm.php:44`, `GoogleMaps.php:46`, `PowerBI.php:64`), which
  is not a valid `data-component-width` value, so those embeds get no width treatment.
- **Storybook title paths do not match the tier directories in three places.** The four banner
  components live under `02-molecules/` but are titled `Organisms/Banners/...`; `read-time`
  lives under `02-molecules/` but is titled `Atoms/Read Time`. The **Tier** column follows the
  Storybook title, since that is what a reviewer sees.

## Coverage and scope

Every component in `01-atoms`, `02-molecules` and `03-organisms` is accounted for, as the
ticket requires. `00-tokens`, `04-page-layouts` and `05-page-examples` are out of scope.

- **63 props files → 281 controls**, all inventoried. A guard test
  (`components/_storybook/control-parity-audit-coverage.test.mjs`) fails the unit suite if a
  control is added to any props file without a row appearing here, so this document cannot
  quietly go stale.
- **4 components have a story but no props file**, and are covered directly from their story:
  `Atoms/Table` (no controls), `Molecules/Modal` (no declared `argTypes`), `Organisms/Galleries`
  (one control, `gridHeading`), and `Templates/Two Column (70/30)` (no controls — see below).

  covers them** — for example `01-atoms/controls/*` under `Atoms/Controls`, the four
  `02-molecules/banner/*` directories under their respective banner stories, and

### Two Column (70/30): a story was added, and it has no Storybook controls

This audit originally listed `03-organisms/layout/two-column` among the components with no
Storybook presence. That was a real gap rather than an acceptable exception — it is an
editor-reachable section, it is squarely in scope for the colour work, and "inventory covers
every component" cannot be satisfied for a component with no story to source a control list
from. `components/03-organisms/layout/two-column.stories.js` now renders it, using the
`_two-column--example.twig` that was already in the tree and referenced by nothing.

It declares **no Storybook controls**, and the Drupal side is missing two of the three section
dials — but not, as an earlier draft of this section claimed, all of them:

- `ys_layouts.layouts.yml:14` registers `ys_layout_two_column` with **no `class:`**, unlike
  `ys_layout_two_column_50_50` and `ys_layout_three_column_33_33_33`, which both point at
  `YSLayoutOptions`. `YSLayoutOptions.php:73,86` is the *only* source of the **divider** and
  **component theme** settings, so a 70/30 section gets neither.
- **Padding is the exception, and it is genuinely editor-settable.** No `class:` does not mean
  no settings form: Drupal core defaults the plugin to `LayoutDefault`
  (`core/lib/Drupal/Core/Layout/Attribute/Layout.php:88`), which implements
  `PluginFormInterface`, so `ChooseSectionController.php:81` still routes a 70/30 section
  through Configure Section. `ys_layouts_form_layout_builder_configure_section_alter()`
  (`ys_layouts.module:380`) is a `hook_form_FORM_ID_alter()` keyed on the **form ID, not the
  layout plugin**, so it adds the `padding_options` select unconditionally, and
  `ys_layouts_preprocess_layout()` (`ys_layouts.module:434-444`) maps it onto
  `settings['padding']` for every layout alike.
- So `layout--two-column.html.twig:20`'s `settings['padding']` read is **live wiring, not
  dead** — an editor really can set padding on a 70/30 section.
- **Width is inert everywhere, not a dial this section lacks.** No multi-column section has an
  editor-settable width: `layout--two-column--50-50.html.twig:19-24` passes only
  `component__layout`, `layout__padding`, `layout__divider` and `component__theme`, and
  `layout-props.yml` declares those same four and no width. `yds-layout.twig:21` accepts a
  `component__width` that nothing in `yalesites-project` ever supplies.

That makes **padding a `Drupal-only` control on this component** — the one new inventory row
this section adds, now carried in the *Drupal-only controls* table above and recommended
`Add to Storybook`. The editor has it; Storybook cannot show it, because `yds-two-column.twig`
emits no `data-component-padding` at all, while the Drupal template at
`layout--two-column.html.twig:20` does. The two templates have drifted: the Drupal one is
bespoke and never includes `yds-two-column.twig`. (They also disagree on markup — CLT wraps the
secondary region in an `<aside>`, `layout--two-column.html.twig:28` in a plain `<div>`.)

**Why this is a colour-surface finding and not just bookkeeping.** A 70/30 section can never be
given a theme, so it always renders on the ambient page surface while the 50/50 and 33/33/33
sections beside it can be themed. Whether that is deliberate or an oversight is a design call
for the review — it is the one disposition on this component worth ratifying. The new story is
where it can be looked at: use the global theme toolbar to see the section against each
palette, which is its only colour variation.

The story is deliberately **not** a visreg story. Adding snapshots carries visual-regression
cost and belongs with whatever the review ratifies, not with an inventory ticket; the
component still has no automated contrast coverage, and that gap is recorded here rather than
closed.

## Documentation impact

The ticket asks whether the `*.mdx` docs will need updating once controls are dropped or
migrated. **Partly automatic, partly not.**

- **The props tables update themselves.** 61 of the 62 mdx files render their properties table
  with `{twigPropsTable(componentProps, ...)}` sourced from the same props file that drives the
  Storybook controls, so removing a control from props.yml removes it from the docs table with
  no doc edit. (`01-atoms/tables/tables.mdx` is the exception, consistent with `Atoms/Table`
  having no props file.)
- **The prose and the demo sections do not.** Divider is the worked example: its mdx opens
  "Horizontal rules with customizable thickness, width, colour and positioning" and carries a
  whole `## Thickness Variations` section rendering a `DividersThickness` story export. Dropping
  `thickness` needs a prose edit, a section removal **and** a story-export removal.

So budget per-component doc work for anything dropped, and none for the table itself. No doc
changes are made in this ticket.
